# Build Decision Record — 1.2.0

1. **Real task:** Put the existing single-file weather calendar on an easy-to-share H5 URL, make the supplied WeChat contact usable, expose a small AI-callable API, and keep README downloads on the latest release.
2. **Step 0 classification:** **Improve**. Workspace/repository inspection found no OpenAPI or AI API module. GitHub repository search for weather-calendar OpenAPI/API found no directly reusable project; reuse the existing app, Node server, and bundled `lunar-javascript`; OpenAPI 3.1.1 is the interoperable contract. GitHub Pages is used for static hosting.
3. **Execution verdict:** GO for the user's requested public repo update, version release, and static H5 publication. Only project assets, code, public calendar data, and the supplied QR crop are in scope.
4. **Measurable difference:** one stable mobile entry URL; 24 solar terms returned per supported year; calendar dates require no AI credentials; weather calls require an operator token; latest-download URL stays stable across versioned Releases; no new runtime package.
5. **Success evidence:** decode the cropped supplied QR, browser-check H5 redirect and share/contact links, run API/reward tests, validate the OpenAPI document and static build, verify release download and deployed Pages URL.
6. **Minimum core:** root redirect, Pages workflow, corrected pay/contact paths, one API router module, three documented endpoints, OpenAPI schema, tests, updated README and release archive.
7. **Plugin boundary:** AI endpoints stay in `server/plugins/ai-api.cjs`; OpenAPI is the integration contract. Existing share/reward/payment application flow remains separate. No AI-provider SDK or provider-specific adapter is added.
8. **Local-first boundary:** browser weather history and location remain local. The API reads no browser history or referral ledger. Only explicit weather coordinates are sent to Open-Meteo; Pages hosts static public files.
9. **Data classification/transfer:** repository contents are Public for the requested GitHub update. The screenshot profile details are excluded; only the QR crop and explicitly supplied `chat-tea` identifier are used. API token and reward ledger remain operator-local/private. AI callers receive only the date or forecast fields they request.
10. **Public release decision:** authorized by the user. Review staged diff, archive contents, image crop, and secret scan before pushing/tagging/releasing; no ledger, token, screenshot header, or test data is included.
11. **State/check rule:** Pages must deploy from `main`; latest stable asset name is `sayelf-qingyubiao-latest.zip`; API routes are stateless except for upstream request handling and never write the reward ledger.
12. **Epistemic labels:** Fact — current UI is a responsive HTML5 app and includes Node reward server/lunar code. Observation — it has no public H5 launcher or AI schema and its existing Node server did not serve the payment page/QR. Inference — a static GitHub Pages launcher improves reach without rebuilding the UI. Hypothesis — OpenAPI import will reduce provider-specific integration work; this requires the target AI platform to support OpenAPI tools.
13. **Evolution/rollback:** release as v1.2.0; revert to v1.1.0 commit/tag to roll back code and Pages deployment. Keep operator data directory backed up separately; rollback does not reverse already-earned rewards.
14. **WebUI decision:** Required; reuse the existing UI and publish it as static H5. The root page only forwards to the existing app; no second interface is created.
15. **Simplest implementation:** native HTML redirect, GitHub Pages maintained actions, Node standard library, existing bundled calendar library, and an OpenAPI 3.1.1 YAML contract.
16. **Explicitly not built:** PWA/offline service worker, accounts, payment automation, new AI SDKs, public weather API hosting, or broad UI rewrite.
